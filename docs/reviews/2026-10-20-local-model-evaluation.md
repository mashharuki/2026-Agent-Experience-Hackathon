- Decider revision `216d1ccb46a9e9b036eb9187b248db98480f77d4`、ベース `b1485b2fa6dfa1287294f269f5fb618e03d52d7c`。既存キャッシュのhead／LoRA／tokenizer／ベース重みを検査。取得・AWS・Bedrock・実写真の使用なし。
- HF／Transformersのoffline設定と外部socket・AWSクライアント生成の禁止下でロード・実行。モデルのstdout／stderrを公開結果へ流さず、結果には合成ID・enum・数値・hashだけを記録。

## データと採否の事前固定

合成観察・希望・制約のdev10件、holdout30件。通常／禁止・矛盾／不鮮明／曖昧さ／上限の5分類で各2／6件。期待値は予測前に固定し、モデルへ渡していない。JSONLのSHA-256は以下。

- dev：`675d391fd35a3a9d5ac17e5a116958307771b284034ce092cb44fa75286f2866`
- holdout：`296eede3fbf9b11e721e0264072e74f832b09cd22b288fdc2a276ce3a9fef08d`

作者はAIエージェント1名。独立した人間・専門家のレビューはない。計画時の人手合成という想定との差分であり、今回の結果を人間の合意ラベルと表現しない。類似する制約・判断パターンは両splitに含まれるため、完全に独立した汎化性能の証拠ではない。group_idの検査は宣言した原例群の跨がり、入力検査は完全一致の重複を防ぐもので、意味的な重複の自動検出ではない。

devは各版3反復。調整を加えず、v2の状態文・実行条件・採否条件を固定してからholdoutへ進めた。holdoutは30件×3反復×2版＝180判断で、独立した180事例ではない。ルールも同じ30件を3反復するが実モデル判断には数えない。

G3は最終制約違反0、群別の最終適合率と支援可能例での支援率に退行なし、状態情報に関連する改善が少なくとも一例あること。等価・悪化ならv1を維持する。confidenceは正解確率へ読み替えず、閾値の自動有効化をしない。

## 開発結果

| 方式 | 生の選択適合 | ガード後の適合 | 最終制約違反 | 支援可能例で一手 |
| --- | --- | --- | --- | --- |
| rules-v1 | 27/30 | 30/30 | 0 | 6/6 |
| decider-v1 | 18/30 | 27/30 | 0 | 6/6 |
| decider-v2 | 18/30 | 27/30 | 0 | 6/6 |

現行v1の実装前基準値30判断と、共通入力へ接続した後のv1は、選択と確率が全30判断で一致した。ガード前／後の適合と制約違反を分けており、`offer_finish`を無差別に出すfakeは支援率の検査で不合格になる。

開発例では、対象への接触禁止に対して確認ではなく終了を選ぶ、両部位禁止や最終解析でも一手を選ぶ、回答済みでも再確認を選ぶ場面があった。上限・両部位禁止はガードで終了へ変わる。安全な終了でも、固定ラベルが求める確認と違えば「不適合」であり、その全てを安全違反とは数えない。

状態文が途中で切れていないことも別途検査した。SDKと同じtokenizer・prompt rendererで、問い151token、状態の許容枠3,945tokenに対し、最大v1 135／v2 190token。追加情報が切り捨てられたために変化しない、という説明は今回の入力には当てはまらない。

## 実行・成果物

`apps/worker/`でインストール済みPython 3.12の`.venv/bin/python`を使用。正規の依存管理は既存uv、追加依存なし。

```bash
uv run --frozen --offline python -m tools.evaluate_decisions validate --cases-dir evaluation/cases
uv run --frozen --offline python -m tools.evaluate_decisions run --backend decider --paired-versions v1,v2 --split holdout --cases-dir evaluation/cases --model-cache /absolute/path/to/hub --repeats 3 --max-calls 180 --max-seconds 1800 --out ../../report/model-evaluation/new-holdout
uv run --frozen --offline python -m tools.evaluate_decisions compare --runs ../../report/model-evaluation/2026-10-20-paired-holdout ../../report/model-evaluation/2026-10-20-rules-holdout --cases-dir evaluation/cases --out ../../report/model-evaluation/new-comparison
```

`compare`の5は採用ゲート不合格であり、コマンド自体の実行失敗と区別する。runの0も品質の保証ではない。

ignoredな`report/model-evaluation/`にmanifest、全trial、summary、失敗一覧、候補固定とtoken監査を保存。初回のキャッシュ事前検査はHubの二重symlinkの解釈不備で失敗し、実モデル判断0回。LFSのSHA-256を検証する修正とテストを加えて再実行した。検査を緩めたり重みを取得したりしていない。

実験後、非モデル方式の`load_seconds`は実行時間を含めず0とするようメタデータ処理を修正し、fake回帰を追加確認した。公開ケースのgroup説明も、意味的独立性を保証しない記述へ明確化した。JSONL・期待値・モデルの問い／状態文／ガードは変更しておらず、今回の選択結果・採否に変更はない。

## 限界とAWSへの引継ぎ

- 期待値には単独作者の判断が入り、構造化された撮影不良・制約が多い。固定ルールが有利な設計であり、モデル／ルールの優劣一般を示さない。
- 観察が正しいか、具体的な助言文が安全か、本人が写真を選べるかは評価対象外。画像・Bedrock・実機・AWS性能は未検証。
- 反復を独立標本に数えず、一般精度、p95、統計的有意差、Fargate時間・費用への換算をしない。
- 固定評価の結果・採否・回帰を確認してからT124へ進む。今回の依頼でAWS操作は行わない。
- 次に選択を改善するなら、解析残枠・回答済みをどの四択へ接続するかを問い・選択肢の説明で明示する別実験を考える。単なる状態追記の改善効果を今回確認したことにはしない。期待値も人が確認し、既に結果を見た今回のholdoutは開発用へ移し、新しい固定評価を準備する。
