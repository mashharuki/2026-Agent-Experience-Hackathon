# 観戦ゲームの体験・海面表現 改善計画

作成: 2026-10-23。状態: 提案のみ。実装・依存追加・AWS変更は行わない。

## 1. 目指す体験

**海を読み、推し艇を選び、AIの一手に反応し、勝敗の分岐点を見返したくなるセーリング中継。**

海の高精細化だけでは予想の楽しさは増えない。「ブローの発見 → 艇の選択 → 加速・交差 → 順位変化」を、海面・艇の動作・中継UIでつなぐ。

## 2. 調査範囲と現状

localhost:5174の出走前画面、ObserverApp.tsx、presentation.ts、scene.ts、ocean.ts、boat-visual.ts、DESIGN.md、003の仕様・既存改善計画を確認。今回は全レース・全端末の操作検証や性能測定は未実施。以下の改善効果は検証前の仮説。

既に独自shaderの波、Fresnel反射、日光、雲、ブローの暗色化、引き波、艇のヒール、2人の乗員、3視点、順位、予想固定、判断ログ、結果、コース図リプレイがある。ゼロから作り直さない。

結果の的中表示、予想艇の強調、距離差、終了確認、トークン化、艇名ラベルはソースに実装がある。既存design-improvement-plan.mdの未チェック項目を、そのまま未実装と判定しない。一方、開いていた画面には旧計器・艇速中心の順位表示が残っており、実行中ビルドとソースの一致は次回実装の最初に確かめる。既存の完了項目を重複実装しない。

## 4. 海・艇のリッチ化

### 現行実装から分かる主な制約

- ocean.tsの大きな波は固定方向・振幅の3つの正弦波。風速は主に泡、ブローは色と細波へ反映され、波の大きさや方向は海況に追従しない。
- 空の反射はshader内の近似色。艇・帆そのものを水面に映す反射パスはない。
- scene.tsの上下動は波高を使うが、ピッチは別の正弦波、ヒールは主に艇速・タック側から算出。クルー位置は左右の値を切り替え、動作の連続性が弱い。
- 帆には立体形状と縫い目があるが、膨らみは静的。タックでの抜け・張り直しが見えにくい。
- 品質切替は主にDPR。波メッシュ・反射・泡・影の独立した品質制御が必要。

| ID | 優先/規模 | アプローチ | 実装上の注意 |
|---|---|---|---|
| V01 | P1/M | 海・空・太陽・帆の露出と色を統一 | 大気遠近、水平線、白帆の階調を整える。ブルームで白飛びを隠さない |
| V02 | P1/L | 複数スケールの方向性のある波 | 第一候補は既存shaderをGerstner系へ段階拡張。うねり/風波/微細法線を分離し、風の変化に滑らかに追従 |
| V03 | P0/M | ブローを「読める」水面へ | 同じ可視pressureから暗さ・細波・泡を駆動。雲の影とブローは区別。追従艇を変えて海全体が変化しないよう世界座標で評価 |
| V04 | P1/L | 空・帆・船体の水面反射 | 高画質のみ低解像度の平面反射を比較試作。中低画質は環境反射。波が高い場合の平面反射の近似誤差を確認 |

巨大な外洋の波を足すより、スナイプの大きさに合う波長・船首の水切り・乗員の動作を優先する。写実的な波浪と、ゲームの近似帆走物理を混同させない。

### Three.js参考例の評価

公式oceanサンプルはWater、Sky、法線テクスチャ、環境マップ等を組み合わせる。Waterは平面反射ベースで、導入だけで艇の浮力や大きな波の幾何形状が完成するものではない。現行の独自shaderにも既に波変位があり、全面置換より反射・空・法線の設計を取り込む方が適していると判断する。

依存はthree 0.180.0。公開最新サンプルとr180にはAPI差があるため、r180の実装を基準に比較する。現行DESIGN.mdは外部画像/HDRI/glTFなしを規定。初期案は手続き生成を維持し、法線画像等を導入する場合はデザイン方針・ライセンス記録・アセット予算を先に改訂する。

- [公式サンプル](https://threejs.org/examples/webgl_shaders_ocean.html)
- [r180サンプルソース](https://github.com/mrdoob/three.js/blob/r180/examples/webgl_shaders_ocean.html)
- [r180 Water実装](https://github.com/mrdoob/three.js/blob/r180/examples/jsm/objects/Water.js)
- [ユーザー提示Reddit](https://www.reddit.com/r/threejs/comments/1u225m2/use_threejs_to_simulate_the_realistic_seas/?tl=ja): 認証要求により本文・動画は確認できず。投稿の技法や性能は未検証。

## 5. 画面の構成案

出走前: 海況の短い説明 → 4艇の方針と配置 → 予想確定 → カウントダウン。
観戦中: 海を最大化。上に順位と予想艇、隅に風/レグ/拡大可能なコース図、下に現在の見どころ1件。詳細ログ・設定は引き出しへ。
結果: 的中/勝者 → 着順 → 転機3件 → その瞬間の3Dリプレイ → 次の予想。現在の結果判定・同着処理を流用。

通常観戦と戦術表示を分ける。海上の矢印・レイラインは任意表示で、最新の風に基づく近似と明記する。見えていない未来のブローを表示・モデル入力へ漏らさない。

## 6. 実装フェーズと受け入れ条件

### Phase 0 — 基準確定（U01、既存改善の照合）

- 現在のビルドを確認し、出走前/観戦/結果/停止/再生を同じseedで記録。
- 1440×900、390×844、横向きで基準画面と性能を採る。対象端末名/GPU/ブラウザー/品質を記録。
- DESIGN.md、既存改善計画、003 spec/plan/tasksの実装済み項目を照合。未実装と改善提案を分ける。
- 完了条件: 優先修正と既存機能が重複しないバックログ、比較可能な画面と性能記録。

### Phase 1 — 予想と戦況理解（U02–10、U19）

- ObserverApp.tsx、presentation.ts、style.css、日英文言を変更。まず画面ごとの情報量を整理。
- 新規race-events.tsを純粋関数として設計。tick/艇ID/イベント種別/観測値を持ち、同じ記録から同じイベントを再現する。
- 判断イベントと物理上の動作完了を分け、順位の一瞬の入替は一定時間確認してから通知。
- 完了条件: 初見利用者が予想艇・追従艇・先頭・次マークを把握できる。予想は開始後変更不可、全艇は推論中も動く。

### Phase 2 — 海と艇の整合（V01–06、性能基盤）

- ocean.tsを波パラメータ/海面材質/空へ分離。wave-field.tsにCPU/GPUで共有する定義を持つ。
- CPUとshaderの高さ・法線・座標を一致させ、波/艇/ブイ/泡に同じsimulation timeを渡す。Gerstner水平変位を使う場合は水面サンプルの対応も検証する。
- 現行反射と低解像度反射を同じ画角・条件で比較して採否を決める。低画質には重い反射を載せない。
- 完了条件: ブローの位置が描画・観測と一致。追従変更で海況が飛ばない。艇の浮き/沈み、近遠メッシュ境界の段差を目視確認。

### Phase 3 — 艇の動作と中継（U11–14、U17–20、V07–11）

- boat-visual.tsへ帆/乗員の表示状態、camera-director.tsへ中継カメラ状態を分離。
- タック/ジャイブ/回航を既存状態から補間。カメラと音は操船/AI受付の状態を変更しない。
- 完了条件: ユーザーのスナイプ経験で、タック、クルーの移動、ジブ、ブーム、風上帆走の見え方を評価。手動カメラ優先と揺れ抑制が働く。

### Phase 4 — 振り返りと再戦（U15–16、U21–23）

- イベントタイムラインと3D再生を追加。描画元をlive/replayで切替し、再生時は実行中runtimeを進めない。
- 必要なら記録にpresentationVersion/波パラメータを追加し旧記録の読み込みを維持。物理/風のversionは表示改善だけで変更しない。
- 完了条件: 停止/スクラブ/再生で海・艇・イベントが同期し、追加推論0件。同着/時間切れ/途中終了/予想なしを正しく扱う。

### Phase 5 — 統合評価

- PCは60fps、低負荷端末は30fpsを目標とし、平均だけでなくp95フレーム時間と長い停止を記録。目標値であり現状の達成宣言ではない。
- 高/標準/軽量でDPR、近景分割、法線詳細、反射解像度と更新頻度、泡数、影を調整。状態を変えず画質だけ下げる。
- 10分連続観戦、複数回の再戦、WebGL context loss、バックグラウンド復帰、日英、キーボード、reduced-motionを検証。
- sailing-sim/regatta-webの既存テストとbuild、イベント/再生の回帰テスト、モックE2E、実ブラウザー目視を実行。描画改修で判断採用・失効・勝敗が変わらないことを確認。
- ヨット経験者/未経験者の小規模試走で「どこを見ればよいか」「何が転機だったか」「再戦したいか」を聞く。見た目だけの自己評価で完了にしない。

## 7. スコープ・費用・設計上の境界

初回の推奨範囲はPhase 0–2。次にタック/クルーと自動中継、最後に3Dリプレイ・継続要素へ進む。

リアルタイム実況はイベントから作る短文を第一案とし、毎フレーム/毎イベントのLLM呼び出しを増やさない。既存のレース後要約は実測ログを入力とし、Deciderが説明文を生成したように表示しない。

描画改善はブラウザー側中心で新しい常時AWSサービスを必要としない。既存の$30/30 worker-hours上限は維持。クラウドAPI契約・認証・利用制限はこの計画で緩めない。

風の遮蔽、艇間の競技規則、波による抵抗、ロールタックの推進効果、プレスタートの駆け引きはUIだけでは実現しない。必要なら別の物理・AI仕様変更として設計し、version更新・公平性・完走率の評価を行う。今回の演出変更へ混ぜない。
