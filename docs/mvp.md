# 撮る前のひと手間：最小版の仕様案

2026-10-17。方向性はユーザーが採用済み。以下の画面・対象範囲・技術分担は、その方向を実装可能な形にする提案であり、すべてを個別にユーザー確認したわけではない。本書は初期案の履歴。現行の実装範囲は [機能仕様](../specs/001-pre-photo-grooming-assist/spec.md)、[技術一覧](tech-stack.md)、[検証記録](reviews/2026-10-19-remediation-validation.md) を参照。

調査と選定根拠：[発散・収束・検証メモ](20261017_strands_decider_idea_review.md)

## 作る体験

証明写真を撮る前に、眉や前髪を一つだけ整えて試し、本人が納得できる仕上がりを選ぶ。

最初の利用場面は「自宅で撮影前の準備をする」。スマホのカメラで顔を確認し、短い助言に従って現実の身支度を変える。最終的な写真と好みを選ぶのは本人。提出先への申請はこの体験に含めない。

最初に確かめる約束は「何をすればよいか分かり、一つ試して、続けるか終えるかを決められる」。仮称は「撮る前のひと手間」。名前は後から変更できる。

## 最小版の範囲

- スマホ向けWeb画面を仮置きする。カメラプレビューは常時表示し、解析は撮影・再確認の操作時に行う。
- 身支度は眉の毛流れと前髪から始める。眉ブラシや髪留めなど、戻せる操作を提案候補にする。
- 光・顔の位置の確認は、前後を比較しやすくするために使う。
- 一度の助言は一つ。変更は一セッションで最大二回。いつでも変更せず終了できる。
- 初版の用途は一つに絞る。調査メモの候補は日本の旅券用写真の撮影準備。助言と規格の説明を区別し、受理保証を出さない。
- 画像の美化加工、眉のカットや抜毛、性別の自動推定、美醜の点数化、メイク全般の診断は初版の対象外。

## 四つの画面

| 画面 | 本人の操作 | アプリの反応 |
|---|---|---|
| 1. 相談する | 「眉」「前髪」「まず見てほしい」を選ぶ。任意で希望を一文入力 | 相談範囲を示し、撮影へ進める |
| 2. 試し撮り | 顔の位置を合わせて撮影 | 観察できるか確認。難しければ撮影条件の調整を一つ案内 |
| 3. 一つ試す | 「やってみる」「別の提案」「このままで終える」を選ぶ | 実施中は新しい指摘を増やさず、「整えたので確認」で再撮影 |
| 4. 比べて選ぶ | 整える前と後を並べて「前が好き」「後が好き」「差が分からない」を選ぶ | 本人の選択を記録。「終える」を主操作にし、希望すればもう一手 |

「まず見てほしい」でも、見える根拠がなければ無理に変更点を作らない。相談範囲を本人に尋ねる選択肢を残す。

手元の道具や時間は、最初にすべて入力させず、必要な提案をする段階で確認する。顔画像がクラウド解析に送られることは撮影開始前に説明する。

## 最初に通すシナリオ

本人：「眉の形は変えたくないけど、毛流れは整えたい」

1. カメラを固定し、最初の一枚を撮る。
2. 観察の根拠を確認する。画像で毛流れを判断できない場合は、本人に気になる箇所を尋ねる。
3. 眉ブラシが使えることを確認し、一つの操作を提案する。
4. 本人が整える。アプリはその間、次の助言を重ねない。
5. 同じ位置と光で再撮影する。比較できないほど条件が変われば撮り直しを案内する。
6. 二枚を本人が比較して終了する。「前が好き」も成功した利用として扱う。

助言文は事前に固定した台本を常に出すのではなく、観察と本人の依頼に根拠がある場合だけ提示する。試作デモで仮画像や再生データを使う場合は、そのことを明示する。

## Bedrock・Decider・通常コードの分担

| 担当 | 役割 |
|---|---|
| Bedrock | 画像の観察、本人の希望に合わせた助言候補、選んだ一手の説明 |
| Decider | 観察と依頼に照らし、身支度の助言・撮影条件の調整・追加確認のどれを行うか選ぶ |
| 通常コード | 画像の有無、明示的な変更禁止、操作状態、二回の上限、写真の表示と本人の選択を扱う |

初版は「Bedrock観察→Decider選択→必要時に説明生成」を仮の構成とする。Deciderの直接画像入力は短い技術試験の対象とし、精度がよいと確認できた場合だけ置き換える。二つの製品構成を並行して作らない。

Deciderへ渡す状態：本人の発言、相談範囲、観察結果と不確かな点、道具、直前の助言、本人の反応。

型付きの問いの案：

> 本人の依頼と今確認できている状態から、次に使う支援はどれか？

候補：`grooming_tip`（身支度の一手）、`capture_setup_tip`（撮影条件の調整）、`clarify`（本人への確認）、`offer_finish`（終了を提案）。

実施中の待機は画面状態を基にコードで扱う。終了操作、明確な禁止、画像欠如もモデルの判断で覆さない。Deciderの判断結果が実際にどのツールを呼んだかを、デモ用の記録に残す。本人向けの画面にモデル名や内部スコアを並べる必要はない。

再利用パターンの中心は「本人の希望と観察の確かさに応じた支援ツール選択」。曖昧な依頼を扱う例と、追加確認を選ぶ例を含める。公開時には質問・選択肢・接続コード・使い方を揃える。

## 最初の検証に使うケース

| ケース | 確認する動作 |
|---|---|
| 眉の形は維持し、毛流れだけ整えたい | 形を変える提案をせず、根拠があれば毛流れの案内を選ぶ |
| 「眉には触れたくない」と明示 | 眉の操作を禁止し、他の許可範囲か終了を扱う |
| 道具がなく、時間も少ない | 買い足しを前提とする提案を出さない |
| 逆光で眉が見えない | 毛流れを断定せず、撮影条件の調整か確認を選ぶ |
| 画像が届いていない | コードで止め、再撮影を案内する |
| 同じ条件の写真を変更なしで再撮影 | 新しい外見の指摘を次々に作らない |
| 身支度中にカメラへ顔を向け直した | 新しい助言を重ねない |
| 前後で光が大きく変わった | 身支度の効果を断定せず、比較条件を整える |
| 本人が「前が好き」と選んだ | 選択をそのまま尊重し、次の変更を強制しない |
| 既に二回試した／本人が終了した | 新たな変更を提案せず終了する |

これらは開発用の例であり、評価用データとは分ける。通常コードで確定できるケースと、モデルの判断品質を測るケースを分けて集計する。

## 次の一歩

まず、同意のある写真で眉・前髪の観察と一手の提案が成立するかを確かめる。その後、実スマホからAWS上の処理へ一往復させ、最小のシナリオを通す。画面全体を作る前に、根拠のない指摘の有無と撮影から助言までの時間を記録する。

開発先とAWS構成・予算は後続の仕様・researchに記録済み。本段落は初期検討時点の手順。実装へ入る時点で確認する。必要な検証人数と合否基準は、発散・収束・検証メモに記載済み。
