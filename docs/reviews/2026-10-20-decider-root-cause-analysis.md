# Deciderが改善しなかった原因の分析

後続の実装方針・v3不採用とv4の検証は[実行可能性分離計画](../../specs/001-pre-photo-grooming-assist/eligibility-plan.md)を参照。本稿の診断結果・旧ラベルは履歴として保持する。

2026-10-20。[前回の比較](2026-10-20-local-model-evaluation.md)を再集計し、原因の切り分けに開発用10例×3条件＝**追加30判断**を実行した。AWS操作・重み取得・本番設定変更はない。[実測・実行条件・全診断結果](2026-10-20-decider-root-cause-evidence.json)を保存した。

## 結論

**状態文に情報を足すことと、その情報を使って判断規則を守れることを同一視したのが、改善方針の主要な問題だった。** 現行モデル・四択では、残枠や回答済みの情報がスコアに影響しても、期待する選択に変わらなかった。

ただし「説明不足だけ」「2Bだから能力不足」とは断定できない。規則を明記する実験では、禁止ケースの一部が改善した一方、上限ケースは改善せず、別のケースに退行も出た。**問い・選択肢の定義と、モデルに任せる責務の両方を見直す必要がある。**

さらに、最終成績に残った唯一の不一致には、プロダクト要件と評価ラベルの不整合がある。モデル単体の誤選択とは別の問題として扱う。

## なぜなぜ分析

| 段階 | なぜ | 確認結果と根拠 |
| --- | --- | --- |
| 1 | v2で成績が改善しなかったのはなぜか | dev10例・holdout30例の全てで、生の選択とガード後の対応がv1/v2で同じだった。反復込みでも不変 |
| 2 | 情報を追加しても選択が変わらなかったのはなぜか | 全40例でスコア分布は変化したが、最大スコアの選択肢が入れ替わるほどではなかった。入力変更は推論に反映されている |
| 3 | 情報が望ましい選択に結び付かなかったのはなぜか | v2は残枠などの事実を追記したが、問い・選択肢は従来のまま。解析3回・確認回答後の扱いが選択肢に明示されていない。明示しても上限2例は誤ったため、文面不足だけでは説明できない |
| 4 | なぜ文章の追記だけで改善する設計にしたか | 「モデルとガードが同じ事実を参照する」という入力整合と、「モデルが規則に従う」という判断品質を、同じ変更で改善できると見込んだ。実際は四択全てを選択でき、事実の追記は候補を実行不能にする処理ではない |
| 5 | なぜその見込みを早期に検証できなかったか | 初回は状態文だけの比較で、情報の有無・問いの定義・規則への追従を分ける診断がなかった。devで不変だった時点で今回の切り分けを先に行うべきだった。採用ゲート自体は機能し、v2の誤採用は防いでいる |

1〜2は測定事実、3はコード上の事実と追加実験で確認した寄与要因、4〜5は設計・進め方の分析である。モデル内部の注意・学習内容を観測できたわけではない。

## 入力不達・切り捨てではない

- SDKの`ask → evaluate → render_state／render_question → 推論`を確認。渡した状態と選択肢が推論に使われ、今回はprefix-cacheも無効。
- 元の問いは151 token、状態の許容枠3,945 token。全40例の状態は最大v1 135／v2 190 tokenで、切り捨てはない。
- holdout30例の、各例における選択肢スコア変化の絶対値の最大値は0.0045〜0.1506、中央値0.0288。入力変更は出力に影響している。全項目を正しく理解した証拠とは異なる。
- 例：`dev-last-analysis`の終了スコアは0.0461→0.1236に上がったが、v2でも一手の0.6839が上回った。
- 追加実験の基準条件は、前回v2の全10例について選択・スコアが完全一致。異なる重みや実行経路を比較したための差ではない。

## 規則を明記する追加実験

同じdev10例、同じv2状態文・モデル・ガード・閾値0を使用。各条件は基準に対して変更するフィールドを一つに限定し、ケースごとに実行順を循環させた。全条件と30判断・600秒の上限を実行前にmanifestへ記録。実際は30/30成功、約171秒。

| 条件 | 変更箇所 | 生の適合 | ガード後の適合 |
| --- | --- | --- | --- |
| 基準v2 | 変更なし | 6/10 | 9/10 |
| 質問文だけ具体化 | 禁止・上限・回答済みの優先規則を列挙 | 7/10 | 10/10 |
| 選択肢説明だけ具体化 | 一手・確認・終了を選ぶ条件を列挙 | 7/10 | 9/10 |

主な変化は以下の通り。

- **眉への接触禁止**：基準の`offer_finish`から、両変更条件とも期待された`clarify`へ変わった。文面設計の寄与は確認できた。ただし質問文版の1位と2位の差は0.0018で、安定性の保証にはならない。
- **両部位の接触禁止**：基準の`grooming_tip`に対し、質問文版は`clarify`、選択肢説明版は正しい`offer_finish`。記載箇所によって結果が異なる。
- **最終解析・確認回答済み**：両変更条件とも生の選択は不適合。ガードが終了へ補正した。規則を日本語で書けば安定して守れる、という仮説は支持されなかった。
- **曖昧で観察根拠のない相談**：選択肢説明版で、正しかった`clarify`から`grooming_tip`へ退行。この例は既存ガードでも補正されず、最終適合も悪化した。文面を詳しくすれば必ず改善するわけではない。

**「情報不足だけ」が原因という仮説は棄却する。問い・選択肢の表現は寄与要因だが、それだけで上限規則を解決できていない。** 既知の開発例による診断であり、いずれも本番採用していない。文面の長さ・具体性・優先順位を個別に分離した実験ではなく、その各寄与や、日本語・モデル規模・学習データの影響は未特定。

## 評価側の問題

### 最終成績だけでは問題が見えにくい

元のholdoutを独立した30場面で数えると、生の正解19例＋ガードで補正10例＝最終29例だった。通常・不鮮明・曖昧さは既に各6/6で、最終成績の改善余地は小さい。

ただし、これは「生の選択も不変」の理由にはならない。初回集計とG3は生／最終を両方見ており、ガードの存在を不採用の原因にはしない。引き続き生の適合・上書き・最終適合を別々に追う。

### 安全な終了を誤りとしたラベルの根拠が弱い

`holdout-brow-blocked`は接触禁止に対し`offer_finish`を選んだため不適合になった。一方、[specのUser Story 2](../../specs/001-pre-photo-grooming-assist/spec.md)は「他の許可範囲の助言か終了」を認める。評価は`clarify`だけを許容し、終了を必ず誤りとする十分な根拠がない。

独立した人間のラベルレビューがなかったことも、この不整合を残した要因である。元の結果をよく見せる事後的な再ラベルは行わず、要件と許容集合をレビューし、新しい評価版で解決する。

### 状態の表現にも曖昧さが残る

v2の「接触可能な相談範囲」は現在選択中の対象だけで算出する。眉は禁止・前髪は禁止でない場合でも、相談対象が眉なら「なし」となる。「現在の対象に触れられない」と「他の対象にも触れられない」を区別できていない。

これはコード上で確認した表現の問題で、「現在の対象への接触可否」と「本人に確認すれば相談できる他の対象」を分けるべきである。ただし同じ終了選択はv1にもあり、この項目だけを変える実験はしていないため、最終不一致の原因とは断定しない。

## 修正方針

1. **上限・禁止・質問回数はコードで保証する。** 状態遷移を文章の理解だけに任せない。今回の退行を踏まえ、観察根拠なしの一手を防ぐ条件も、要件と対応するガードの不足として別途設計・回帰検証する。
2. **モデルの判断と実行可能性を分ける。** 実行可能性は確定済みの状態から決め、モデルは許された支援の中で希望と観察に合う案を選ぶ設計を検討する。四択IDと選択が動作につながる要件を保持し、仕様・ハンドラー・評価を更新してから実装する。
3. **問い・状態・正解集合を揃える。** 終了を許す条件、確認が必須の条件、現在の対象と他の許可対象を明文化し、人間にラベルを確認してもらう。文面変更では正解例の退行も確認する。
4. **新しい評価セットを固定する。** 今回のholdoutは既に見たデータなので、今後の調整では開発用とする。意味的に似た原例の分割も見直し、反復を独立事例として数えない。

本番は`QUESTION_VERSION=v1`、confidence閾値0を維持。モデル差替え・英語化・fine-tuningが必要との結論は出ていない。新設計の実装とAWS検証は今回の範囲に含めない。

## 再現と確認

[診断ツール](../../apps/worker/tools/diagnose_decider_policy.py)はdev専用。正解ラベルは選択後の集計だけに使用。ネットワーク・AWSクライアント生成を禁止し、取得済みの固定重みを使う。出力先の再利用は拒否し、入力本文は出力しない。

`apps/worker/`から実行する。

```bash
uv run --frozen --offline python -m tools.diagnose_decider_policy --model-cache /absolute/path/to/hub --out ../../report/model-evaluation/new-policy-diagnostic
```

診断コードのRuff成功。既存の評価ケース・通信禁止・タイムアウト・集計のpytestは32件成功。データJSONL・元の問い／状態文・ガードのハッシュが前回から不変であることも照合した。今回の30判断は前回275判断と別に記録する。
