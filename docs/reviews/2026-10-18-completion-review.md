## 技術面の強み

- Nova Liteによる観察、Deciderによる支援選択、コードによる制限、本人による最終判断という責務分離が明確。
- Cognito、API GatewayのJWT認証、所有権検証、署名付きアップロード、画像・自由文のログ抑制が揃う。
- OpenAPI YAMLを正本にしてConnexionとOrvalへ接続している。複数言語間の契約を管理しやすい。
- 利用枠、再配送、実行リース、重複推論の抑制、ワーカーの起動停止を設計している。
- CPU上のDeciderをFargateで動かす構成を実装し、他の用途でも使える判断パターンを切り出している。

Fargateは起動中の料金が発生するため、「アクセスがないと自動的に費用ゼロ」とは説明しない。低コスト性は起動時間、利用件数、モデル呼び出し、失敗・待機分を含めて実測する。AWSクレジットの適用可否は保有クレジットの条件で別途確認する。

## 優先して修正する事項

P1は中心体験または障害復旧に関わるため、利用者に試してもらう前に優先する。P2はその次の品質・運用改善。

### R1 / P1 — 明示的な禁止事項が画面から構造化データへ届かない

根拠：`apps/frontend/src/screens/Consult.tsx:25`、`apps/frontend/src/features/session/SessionFlow.tsx:163`、`apps/api/src/photoprep_api/services/session.py:52`。

画面はscopeとwishを送るが、restrictionsを送らない。自由文に「眉の形は変えたくない」と書いても、サーバーに保存されるrestrictionsは空配列になることを確認した。モデルが自由文を尊重する可能性はあるが、構造化された禁止事項を使うコードのガードには届かない。

**修正方針：** 禁止事項の選択UIを設け、契約のenumで送信する。自由文から抽出する場合も、本人が確認した制約を確定させる。画面入力→API保存→モデルが禁止行動を返す→コードが拒否、まで一つの回帰シナリオにする。

### R2 / P1 — clarifyに回答する経路がない

根拠：`apps/frontend/src/features/session/SessionFlow.tsx:135`。

clarifyをcapture_setup_tipと同様に処理し、説明を表示して再撮影へ戻している。質問に答えてscopeや希望を更新する入力・API経路がない。質問の内容によっては回答できず、再解析だけで利用枠を消費する。

**修正方針：** 確認質問専用の画面状態と回答APIをOpenAPI YAMLから追加する。回答が次の判断状態に反映されることを検証する。単なる回答のための画像再送・有料推論を避ける。

### R3 / P1 — ジョブ作成途中の障害でセッションが復旧できない

根拠：`apps/api/src/photoprep_api/services/analysis.py:94`。

冪等性レコード、アップロード使用済み、セッションの解析中状態、JOBを別々に保存している。JOB保存で例外を注入すると、セッションはANALYZING、analysesUsedは1、JOBは存在しない。同じキーで再送しても存在しないjobIdが返る。PENDING_DISPATCHの再送処理もJOB不在には対応できない。

**修正方針：** 条件付きTransactWriteItemsで、同一DynamoDB内の予約・状態・JOBを原子的に保存する。SQS送信は既存PENDING_DISPATCH方式で後続処理にする。各保存境界での障害と競合をテストする。セッション作成の冪等性・利用枠にも同じ観点で点検を広げる。

### R4 / P1 — ポーリング失敗時に待機から抜けられない

根拠：`apps/frontend/src/features/session/useAnalysis.ts:40`、`apps/frontend/src/screens/TrialCapture.tsx:72`。

ジョブ取得エラーを画面状態へ反映していない。最初の取得から失敗し続けるとcurrentがなく、タイムアウト表示を更新するeffectも処理しない。ポーリング間隔が終了条件に達してもwaitingが残り得る。さらに解析中は終了ボタンが無効になる。

**修正方針：** HTTPエラー処理と、レスポンス更新から独立した期限タイマーを追加する。待機中にも終了できるようにし、ポーリングの中断・写真メモリの解放・遅れて返る結果の無視を行う。401、連続5xx、応答停止、終了後の遅延応答をテストする。

### R5 / P2 — 画像掃除が部分削除失敗を成功として報告する

根拠：`apps/api/src/photoprep_api/ops/sweeper.py:34`。

DeleteObjectsの戻り値を確認せず、削除対象数をdeletedとして返す。fakeがAccessDeniedを返してもdeleted: 1となることを再現した。S3の一括削除はHTTP成功時にも個別エラーを返し得る。[AWS API仕様](https://docs.aws.amazon.com/AmazonS3/latest/API/API_DeleteObjects.html)

**修正方針：** Errorsを確認し、成功件数・失敗件数を分ける。失敗を監視できるようにし、再試行可能な失敗と権限問題を区別する。全部成功・一部失敗・全部失敗をテストする。ログには画像や個人情報を含めない。

### R6 / P2 — 開発時のモック選択と実応答が一致しない

根拠：`apps/frontend/src/App.tsx:69`、`apps/frontend/src/main.tsx:9`。

useState初期化関数がモック生成とグローバルfetch変更を行う。開発時のStrictModeでは初期化関数が再実行されるため、画面が保持するモックとAPI呼び出し先が異なるインスタンスになり得る。実際に「あいまい（確認の質問）」を選んでも通常の助言が表示された。原因はコードからの推定であり、修正後にStrictModeでの再検証が必要。

**修正方針：** 初期化を純粋にし、APIクライアントへ同じモックを注入するなど、画面設定と通信先の所有関係を揃える。StrictMode下でシナリオ切替→実応答まで確認する。

### R7 / P2 — 品質チェックを継続的に通せる状態にする

Knipは失敗した。生成コード由来の指摘と実際の不要依存を分ける必要がある。リポジトリ内にはGitHub Actionsのワークフローを確認できなかった。外部CIの設定状況は未確認。

**修正方針：** CDKのentryを設定し、生成コードは適切な範囲で除外する。uvなど外部実行コマンドの扱いを明示する。手書きの未使用コード・依存は用途を確認して整理する。その後、型検査・ビルド・各テスト・OpenAPI生成差分・lint・KnipをCIで実行する。生成コードの指摘を理由に全体を無効化しない。

## プロダクトとしての評価と検証方針

魅力は「顔を採点する」のではなく、撮影直前に自分で選べる小さな行動へ落とした点にある。二回までという終了条件と、本人がbefore/afterを選ぶ設計も体験を説明しやすい。

一方、通常の身だしなみチェックリストに対して、写真をクラウドへ送る価値が十分あるかは未検証。認証・同意・撮影・解析の手間もある。対象をプロフィール撮影など一つの場面に絞り、同意を得た少人数で、迷わず完了できるか・提案を実行できるか・撮影に進む助けになったかを確認する。外見の良さを成果指標にしない。

モデル評価は開発例と別のケースで実施する。禁止事項、暗い写真、対象が写っていない写真、判断が難しい状態、二回目の終了を含める。ルールのみ／LLMのみとの比較は、小さな同条件の評価でもDeciderを使う理由を説明する助けになる。現段階では精度、低コスト、低遅延の優位性を断言しない。
