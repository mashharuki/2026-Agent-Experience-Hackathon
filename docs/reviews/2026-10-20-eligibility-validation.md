# 実行可能性分離の実装・検証結果

2026-10-20。[原因分析](2026-10-20-decider-root-cause-analysis.md)に基づき、**コードで実行可能な候補を決め、複数候補のみDeciderへ渡す**処理を実装した。既定はv4、confidence閾値0。[実測集計・実行条件](2026-10-20-eligibility-validation-summary.json)を保存した。AWS操作は行っていない。

## 実装

- `support_policy.py`：解析3回・変更2回・両対象禁止は終了のみ。一手には空白でない根拠・接触許可・既知の良好な光と構図・afterなら比較可能であることを要求。確認はbefore・未回答の場合のみ許可する。
- `decision_pattern/`：許可候補だけを実際のChoiceQuestionへ渡す。候補外の応答や、除外した行動を復活させるガードは、ハンドラーを実行せず失敗とする。
- 候補一つならDeciderを省く。`decision_source=policy`と理由・候補を記録し、モデルの選択・確率・confidenceはnull。モデルを呼んだ場合は実際の候補集合に対するスコアを保存する。旧記録は後方互換で読む。
- 状態文では「現在の対象に触れられるか」と「確認後に選べる他の対象」を区別する。v4は従来の問い・選択肢の表現を保ち、候補制御と追加状態を組み合わせる。
- afterで比較不能かつ終了なら、共有状態をDONEへ進め、画面も再撮影待ちへ戻さない。比較可能なら終了提案でも比較・本人の選択を残す。

四択ID、OpenAPIの構造、認証・所有権・終了競合・画像削除は維持。新規依存なし。Decider省略は観察モデルまで省略するという意味ではなく、本番パイプラインの画像観察は残る。

## 文面変更候補v3は棄却

最初に、候補制御に合わせて問い・選択肢の表現も変更したv3を検証した。新しい`policy-cases`は推論前に固定したdev10／holdout30。holdoutでは最終28/30・制約違反0だったが、通常の一手が旧版の6/6から4/6へ減り、事前の退行禁止ゲートを通らなかった。

このためv3は不採用とし、従来の表現を使うv4を別版にした。既に見た`policy-cases`は回帰用へ移し、v4の30/30・支援6/6を確認した。これは新しい独立評価の成功として数えていない。v3のコード・文面と失敗結果も保持している。

## v4の固定確認データ

別の`eligibility-matrix`を推論前に固定。眉／前髪、5分類、回数・回答済み・根拠・比較可否・未知条件を組み合わせた合成dev10／holdout30。devはファイル検査のみで、今回の新しい実モデル比較はholdout30例×1反復×2版。モデルの重み・CPU・ガード・閾値は同じで、ケースごとに版の実行順を交替する。

ラベルはモデル／policy関数の出力から作らず、各状態の許容集合を事前に記述した。接触禁止時の確認と安全な終了の両方を認め、一手を出せる通常例では支援率を別集計する。過去の`evaluation/cases/`のJSONL・ラベルは変更していない。

作者はAIエージェント1名で、人間の独立レビューは未実施。新しい入力・群IDであっても、同じ政策パターンが繰り返される合成の状態行列であり、意味的独立性・代表的な利用者・専門家合意は保証しない。

| 固定確認30例の方式 | 最終適合 | 制約違反 | 支援可能例で一手 | 実モデル判断 | コード決定 |
| --- | --- | --- | --- | --- | --- |
| v1の問い・状態＋従来ガード | 22/30 | 8 | 6/6 | 30 | 0 |
| v4の実行可能性制御 | **30/30** | **0** | **6/6** | **18** | **12** |

v4は5分類すべて6/6。実モデルを呼んだ18例は18/18が許容集合内で、コード決定12例をモデル適合の分母へ足していない。両版30試行ずつに失敗・未実行はない。候補集合が異なるため、旧四択スコアと候補絞込み後のスコアを直接比較してモデル性能向上や校正を主張しない。

事前のゲート（完遂・制約違反0・分類別適合と支援に退行なし・全選択が候補内・意味のある実モデル判断あり）に合格した。**確認できたのは合成データ上のシステム動作の改善であり、モデル自体が賢くなったという結論ではない。**

## 実行量・中断の扱い

| 完了したrun | 予定試行 | 完了した実モデル判断 | コード決定 |
| --- | --- | --- | --- |
| v3開発10例×2版 | 20 | 16 | 4 |
| v3固定30例×2版 | 60 | 48 | 12 |
| v4回帰30例×2版 | 60 | 48 | 12 |
| v4新確認30例×2版 | 60 | 48 | 12 |
| 合計 | 200 | 160 | 40 |

新確認の初回起動は既存runとの重複を止めるため中断した。完了結果は0件だが、最初の判断のactive記録があり、途中のモデル呼出しは最大1件と扱う。これを「推論0回」とは表現しない。partialの証跡は保持し、品質集計には含めず、同じ固定入力・文面で直列に再実行して全60試行を完了した。上表は完了した判断数であり、途中呼出しを含む総開始回数ではない。

通常runは並列モデルプロセス1、CPUスレッド4、seed0、prefix-cache無効。最大20／60試行・600／900秒で監督し、モデル・ベースの固定revisionとローカル重みを検査した。ネットワーク・AWSクライアント生成・自動取得を禁止。前回275判断、原因診断30判断とは別記録。時間差を性能改善やFargate費用に換算していない。

## 再現

`apps/worker/`で、既存ローカルキャッシュと新しい出力先を指定する。既存runの上書きは拒否する。

```bash
uv run --frozen --offline python -m tools.evaluate_decisions validate --cases-dir evaluation/eligibility-matrix
uv run --frozen --offline python -m tools.evaluate_decisions run --backend decider --paired-versions v1,v4 --split holdout --cases-dir evaluation/eligibility-matrix --model-cache /absolute/path/to/hub --repeats 1 --max-calls 60 --max-seconds 900 --out ../../report/model-evaluation/new-v4-validation
uv run --frozen --offline python -m tools.evaluate_decisions compare --runs ../../report/model-evaluation/new-v4-validation --cases-dir evaluation/eligibility-matrix --out ../../report/model-evaluation/new-v4-comparison
```

通常CIは決定的な回帰と3つのデータ版の検査のみで、重み取得や実モデル判断を実行しない。外部API契約に変更がないためOrvalの生成物は変更していない。
